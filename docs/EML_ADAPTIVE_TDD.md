# Адаптивний TDD та ARQ-вікно (P7)

Програмна реалізація: [`eml_tdd.h`](../src/lib/OTA/eml_tdd.h), [`eml_transport.h`](../src/lib/OTA/eml_transport.h), [`eml_ack.h`](../src/lib/OTA/eml_ack.h) та [`rxtx_eml_bridge.cpp`](../src/src/rxtx_eml_bridge.cpp). Тести й вимірювальна модель використовують ті самі класи, що й прошивка. Фізичних вимірювань RF/UART/ISR на ES900 у цій сесії немає; P7.5 лишається відкритим.

## Розклад і квоти

Тривалість слота, спільний лічильник і FHSS не змінюються: один hop на пару фізичних слотів незалежно від приймання й того, хто передає. Змінюється власник слота.

| Mode | 4k | 4k+1 | 4k+2 | 4k+3 |
| --- | --- | --- | --- | --- |
| 0, symmetric 1:1 | C | R | C | R |
| 1, coordinator 3:1 | C | C | C | R |
| 2, responder 1:3 | C | R | R | R |

Кожна сторона має щонайменше одну TX/ACK-можливість за 4 слоти навіть за порожньої черги. Ця квота потрібна ARQ та контролю backpressure. Опорні слоти `4k` і `4k+3` мають однакового власника в усіх режимах, тому втрата повідомлення про розклад не забирає весь зворотний зв'язок.

Coordinator порівнює власну чергу та чергу responder з session-bound STATUS. Перехід у 3:1 потребує щонайменше двох повних payload у більшій черзі, співвідношення понад 3:1 та відсутності PAUSE на відповідному приймачі. Нова нерівномірність має бути підтверджена свіжішим STATUS: старе повідомлення «черга порожня» не є достатнім після одночасного надходження даних на обох UART. За збалансованих черг обирається 1:1. Застарілий STATUS (>64 слотів) не дозволяє нову адаптивну домовленість.

Службові повідомлення використовують лише `slot % 8 == 0` для C та `==3` для R. Решта опорних слотів (`==4` / `==7`) лишається для DATA/ACK. За відсутності RF-втрат та PAUSE кожен напрямок має DATA-можливість щонайменше раз на 8 слотів; ACK-можливість — раз на 4. Черга, retry та backpressure можуть додати затримку. P6 band control має пріоритет, а нові band/TDD-переговори не запускаються одночасно.

LQ тепер рахується від очікуваних **peer TX-слотів**, а не від усіх пар: здоровий напрямок із квотою 1/4 не перетворюється на хибний LQ=50%. P6-лічильник утрачених ACK враховує фактичні повтори без просування `acknowledged_bytes`, а не нормальні нові кадри в польоті. Підтверджений peer PAUSE скидає цей лічильник: відмова UART приймача прийняти новий payload не є RF-завадою.

## Узгодження й втрачені повідомлення

Формат використовує 28 B session-bound SYNC envelope з [P6](EML_MULTIBAND.md):

| Payload offset | Поле TDD |
| ---: | --- |
| 0 | незмінна версія EML |
| 1 | PROPOSE=8, ACK=9, COMMIT=10, STATUS=11 |
| 2 | mode 0…2; STATUS — 0 |
| 3 | довжина lease =64 слотам; STATUS — flow bits0…1 та pending bit2 |
| 4…23 | sender/receiver ID, обидва session epoch та configuration ID, як у P6 |
| 24…25 | start slot modulo 65536, кратний 4; STATUS — слот вимірювання |
| 26…27 | ненульовий token; STATUS — кількість байтів у TX-черзі |

На відміну від handshake і P6 band control, заголовок TDD-control несе справжні `ack_num` та `flow_ctrl`. Вони застосовуються лише після CRC, generation/freshness, identity, обох epoch та configuration перевірок. Це дозволяє звільняти ARQ-вікно під час переговорів. UART-payload у SYNC не домішується.

1. C пропонує початок щонайменше через 24 слоти, вирівняний на чотири. R перевіряє mode/token/start та відсутність перекриття попереднього lease й відповідає ACK.
2. C після ACK надсилає COMMIT і озброює lease тільки після фактичного TX report; R — після приймання COMMIT. Повтори COMMIT ідемпотентні.
3. Lease діє рівно 64 слоти. Без наступного успішного узгодження обидві сторони автоматично повертаються до 1:1 на його абсолютному кінці. Прострочена чи незавершена пропозиція не змінює розклад.

Втрата всіх PROPOSE/ACK залишає обидві сторони у старому режимі. Втрата всіх COMMIT може тимчасово дати різні режими: можливі колізії в неузгоджених слотах, але спільні опорні слоти, довжини пакетів, годинник і hop зберігаються. Повернення до 1:1 відбувається не пізніше кінця lease, без скидання UART/ARQ. Окремий справжній обрив RF усе ще запускає P6 emergency/reconnect і його чинний контракт відкидання RAM-хвоста.

Для адаптивного LoRa64 поріг emergency становить 231 мс: щонайменше три опорні peer-можливості плюс RX/phase margin. Для FSK, LoRa32 та вимкненого adaptive мінімум залишається 150 мс. Це поріг початку пошуку, не час відновлення. RX descriptor age обмежено 7 слотами, quiet interval — 9: API працює часом наступного власного слота, який тепер може бути на чотири слоти попереду.

## Короткі ACK

FSK має фіксовані контрольні слоти `slot % 64 == 8` (C) та `==59` (R). Вони однакові для 1:1/3:1/1:3 та не залежать від успіху переговорів. Обидві сторони заздалегідь ставлять `RegPayloadLength=4` у Standby; ISR-safe `SetPacketLength()` не змінює модем, bitrate або FIFO-режим. Пошук HELLO завжди слухає повну фізичну довжину. Неактивний транспорт пропускає короткий слот і продовжує handshake у повному.

ACK має 4 B: звичайний 2 B заголовок KEEPALIVE з `payload_len=0`, потім CCITT-FALSE CRC16 заголовка, big endian. Неправильний тип, CRC, довжина, слот чи PHY відхиляються. Дані UART й SYNC там не передаються. У решті FSK-слотів зберігається N=32/64; LoRa SF6 завжди має фіксовані N=32/64 та implicit header.

FSK250 ToA короткого ACK: `(10 preamble + 4 sync + 4 frame) ×8 /250000 = 576 мкс`. Для FSK300 — 481 мкс (лише експериментальний профіль): ToA враховує округлення RegBitrateFrac до фактичних ≈299941 bit/s. Повний FSK300/N64 має ToA 2081 мкс, бюджет 3631 <3700 мкс; попередній номінальний розрахунок P6 давав 2080. Бюджет FSK250 ACK: `500 turnaround +576 ToA +150 IRQ/FIFO +600 processing +300 guard =2126 мкс`, строго менше найкоротшого робочого слота 3100 мкс. Решта повних профілів і бюджетів залишилася [як у P6](EML_MULTIBAND.md#часові-бюджети).

Короткий пакет зменшує RF airtime та SPI-роботу, але тривалість слота зберігається. Додатковий throughput у P7 дає перерозподіл власників слотів. Контрольні слоти забирають невелику частку DATA-можливостей навіть під навантаженням; порівняння нижче включає цю ціну.

## ARQ-вікно

`EmlTransport<Capacity, WindowSize>` підтримує W=1…4, типово 4 у Bridge. Compile-time і runtime-перевірки відхиляють більші вікна: при 3-бітних sequence numbers обидва вікна не можуть займати понад половину простору `0…7`.

- UART-байти зберігаються в початковому TX ring до ACK. Вікно тримає лише довжини й timestamps реально переданих кадрів. Нові кадри заповнюють вікно; за відсутності місця повторюється найстаріший непідтверджений кадр.
- RX має статичні комірки для кадрів поза порядком. Кумулятивний ACK просувається тільки після прийняття неперервного префікса в UART delivery ring. Після заповнення пропуску вже прийнятий хвіст не потрібно передавати повторно. SACK bitmap у wire-формат не додавався.
- ACK може звільнити лише реально переданий неперервний префікс. Timestamp ACK має бути пізнішим за перший TX **кожного** звільнюваного кадра; підготовлений, але непереданий хвіст не підтверджується.
- Повторне отримання не дублює UART-байти, зокрема на відстані рівно 4 у sequence space. Generation, монотонність capture-slot і age<8 захищають від неоднозначності старих descriptor під час wrap. Необмежений RF replay без wire session tag лишається поза гарантією, як у P3.
- Backpressure враховує delivery ring і буфер поза порядком. Звільнення UART повторно просуває готовий хвіст; інакше buffered head міг би назавжди лишитися непідтвердженим після заповнення кількох пропусків. Цей випадок має окремий regression-тест.

Нові метрики API: `inFlight()`, `acknowledged_bytes`, `out_of_order`, TDD mode/stats. Усі transport/controller/CRC-функції працюють foreground. ISR лише читає DRAM-план, вибирає власника/довжину й передає mailbox/ticket; heap або логування там не додано.

## Вимірювання моделі та вибір W=4

Відтворення:

```bash
python3 src/python/test_tools/benchmark_eml_tdd.py --output .venv/artifacts/p7/native-benchmark.json
python3 src/python/test_tools/benchmark_eml_tdd.py --sanitize --output .venv/artifacts/p7/native-benchmark-sanitized.json
```

192 випадки: 4 PHY/N-профілі × 0/10% детермінованих втрат × 6 навантажень × 4 варіанти W/розкладу. Є forward/reverse, symmetric, asymmetric 8:1, короткі повідомлення на тлі bulk і паузи UART. Кожен випадок перевіряє точну доставку всіх прийнятих байтів; результат містить throughput, p50/p95/p99, retransmissions та out-of-order. JSON і CSV створюються разом.

Модель використовує справжній transport/controller, черги 1024 B **на обох сторонах**, UART drain до 64 B за слот і однакові seeds. Латентність рахується від прийняття байта в ring до модельного UART drain. Це не виміри ESP/радіоканалу: SPI/ISR/clock drift, host UART overflow та P6 band/emergency автомат тут не моделюються. Реальний TX має 4096 B черги, тому його затримки при насиченні можуть бути більшими. Час handshake виключений, запуск адаптації включений.

Однобічні 32 KiB, N=64, без втрат:

| PHY | Symmetric W1, B/s | Adaptive W1, B/s | Adaptive W4, B/s | Приріст W4 проти symmetric W1 |
| --- | ---: | ---: | ---: | ---: |
| FSK250 | 7298,81 | 3736,42 | 9664,08 | +32,4% |
| LoRa500/SF6 | 1681,19 | 860,64 | 2304,00 | +37,0% |

Adaptive W1 — навмисний контрприклад у моделі: 3:1 без вікна витрачає додаткові слоти на очікування/повтори. У прошивці W1 автоматично вимикає adaptive. W4 обґрунтовано для узгоджених burst-слотів; у безвтратному 1:1 саме по собі збільшення вікна не дає виграшу.

Приклади latency (напрямок C→R, 0% loss, N=64):

| PHY / навантаження | Варіант | B/s | p50 / p95 / p99, мс | Повтори C |
| --- | --- | ---: | --- | ---: |
| FSK / forward | symmetric W1 | 7298,81 | 135,3 /143,5 /143,5 | 0 |
| FSK / forward | adaptive W4 | 9664,08 | 90,2 /114,8 /172,2 | 1 |
| LoRa / forward | symmetric W1 | 1681,19 | 587,4 /623,0 /623,0 | 0 |
| LoRa / forward | adaptive W4 | 2304,00 | 373,8 /445,0 /640,8 | 0 |

Є компроміси: при симетричному безвтратному потоці adaptive дає 6660 B/s на напрямок FSK проти 7299 B/s baseline, LoRa — 1598 проти 1681. Причина — STATUS/керування та короткі контрольні слоти. P99 короткого зворотного повідомлення на тлі bulk зростає з 4,1 до 12,3 мс на FSK та з 17,8 до 53,4 мс на LoRa. Насичений bulk може мати кращий median та гірший startup tail. Режим 1:1 доступний окремо; модель не доводить перевагу adaptive для всіх навантажень.

## Налаштування та перевірки прошивок

Пара має бути зібрана однаково:

| Flag | Типово | Значення |
| --- | ---: | --- |
| `EML_ARQ_WINDOW` | 4 | 1…4 |
| `EML_ADAPTIVE_TDD` | 1 | 0 — лише symmetric; W1 також вимикає adaptive |
| `EML_SHORT_ACK` | 1 | 0 — усі FSK кадри повні; LoRa завжди повні |

W, розклад, короткі anchors та policy version входять у configuration ID. P6-прошивка не відкриває сесію з P7. Зміни PHY/band/session очищають TDD-план; плановий band handover не скидає ARQ.

Фінальні default-збірки N=64:

| Target | RAM | Flash | IRAM | Вільна IRAM |
| --- | ---: | ---: | ---: | ---: |
| ES900TX | 61 352 | 1 097 677 | 85 420 | 45 652 |
| ES900RX | 43 708 | 510 184 | 33 581 | 15 571 |

IRAM — за ELF boundary symbols. RX timer/DIO/UART call graph: 36 функцій, прямі виклики в IRAM/ROM, 4 непрямі розв'язано в ROM. Recovery/LittleFS/TX THERMAL та виключення RC-баласту підтверджено build audit. Heap/stack під RF-навантаженням і фактичний бюджет foreground 600 мкс ще не вимірювалися.

## Стенд P7.5

[`benchmark_bridge_uart.py`](../src/python/test_tools/benchmark_bridge_uart.py) працює з двома serial-портами одного хоста, перевіряє session nonce/CRC32/порядок тестових записів і вимірює end-to-end p50/p95/p99 одним monotonic clock. Усі записи проходять як звичайний raw UART payload. У прошивці жодного debug-протоколу в UART не додається.

```bash
# Самоперевірка інструмента через PTY, без ES900:
.venv/bin/python src/python/test_tools/benchmark_bridge_uart.py --self-test \
  --duration 0.5 --rate 3000 --drain-seconds 1 --output .venv/artifacts/p7/uart-tool-self-test.json

# Приклад для підключених плат; підставити реальні порти:
.venv/bin/python src/python/test_tools/benchmark_bridge_uart.py \
  --port-c /dev/serial/by-id/TX --port-r /dev/serial/by-id/RX \
  --baud 460800 --scenario all --duration 30 --rate 1000 --output uart-p7.json
```

`--rate` — запропоновані байти тестового потоку за секунду з урахуванням його заголовків. Для насичення піднімати rate поступово; baud не є RF throughput. Host-read-pause зупиняє читання на хості, а не апаратний UART TX приймача без CTS. Фізичний звіт потрібно доповнити платами, firmware SHA, PHY/N/band/power, link load, статичними та runtime memory/ISR вимірами. RF retries не можна визначити з raw UART; для них зняти `emlBridgeTransportStats().retransmitted` до/після через debugger або майбутній status API P8.

PTY self-test пройшов усі шість навантажень. Негативний контроль із навмисною CRC-помилкою правильно видав FAIL. Ці перевірки підтверджують вимірювальний інструмент, а не фізичний UART-міст.
